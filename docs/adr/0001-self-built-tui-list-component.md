# 0001 - TUI 列表交互采用自研共享组件而非 bubbles/list

日期：2026-09-11 ｜ 状态：已采纳 ｜ 出处：tui-ux-driver（grill D1/D8）

## 背景

senv TUI（bubbletea/lipgloss）的 8 个 Tab 各自手写列表渲染、游标与窗口滚动，过滤状态机复制 4 份，多选只在 AI 切换向导存在。统一分组/多选/过滤三类交互需要共享载体；charm 官方 `bubbles/list` 已在 go.mod 中（仅 textinput 被实际使用）。

## 决策

自研薄层共享列表组件（`internal/tui/list.go` 的 `List` + `renderSidebar` + `Filter`），基于既有 `windowedPane` 窗口化原语封装；不引入 `bubbles/list`。Tab 只提供数据行与实体动作，游标/窗口/多选集/过滤状态机由组件承载，按键分发统一走中央 keymap 注册表（`KeyAction`），`?` 键位总览与状态栏提示由注册表渲染。

## 备选方案

- **引入 `bubbles/list`**：自带 keybinding/分页/preview 模型，与本项目的双栏布局、全局键位语义表（r=e 重命名、space 多选等）、All 伪组侧栏范式全面冲突；定制其按键与渲染的成本高于封装自己的原语，且引入第二套交互范式。已否决。
- **最小修补（不建组件）**：三类能力同时铺开而没有共享组件，等于继续制造第 5、6 份复制粘贴。已否决。

## 后果

- 8 个 Tab 逐步迁移后，交互行为与帮助文案结构性一致（同源常量），不可能漂移。
- 组件 API 保持最小面（游标/窗口/选择/过滤挂点），Tab 特有渲染以回调注入；新交互能力先在组件上实现再分发给各 Tab。
- 若未来仍想切换到 `bubbles/list`，需在全部 Tab 迁移完成后重做按键与布局适配，代价显著——这是本决策的主要锁定成本。
